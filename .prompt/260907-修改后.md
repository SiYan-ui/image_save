# 产品需求文档：虚拟养育储蓄应用

## 一、产品需求背景

当前许多年轻人存在“想存钱，但缺少持续动力”的问题。传统记账类应用通常只能记录用户已经花了多少钱，却无法解决用户“为什么要存钱”以及“如何长期坚持存钱”的问题。

本产品希望通过虚拟角色和周期性任务，为用户建立一个具体、持续、有情感连接的储蓄理由。

用户可以在应用中创建一个虚拟的养育对象，例如：

- 婴儿
- 猫
- 狗

养育对象会产生周期性的生活需求，例如：

- 婴儿需要奶粉
- 婴儿需要纸尿裤
- 猫需要猫粮
- 猫需要猫砂
- 狗需要狗粮

未来还可以扩展非周期性的突发事件，例如：

- 感冒、吃药
- 接种疫苗
- 体检
- 宠物驱虫
- 宠物看病
- 玩具或用品更换

当系统根据设定的消耗速度生成一项需求任务后，用户可以在应用外，主动将对应金额存入自己的银行卡、支付宝小荷包或其他储蓄账户，然后返回应用点击“我已存入”，由应用记录本次存入金额。

需要明确的是：

> 本产品不是真实支付工具，也不会自动扣款、连接或操作用户的银行卡、支付宝账户。  
> 应用只记录用户主动完成的存入行为，资金仍然属于用户本人。

因此，本产品不是模拟真实消费，而是：

> 通过虚拟角色和周期性任务，帮助用户建立持续储蓄习惯。

# 二、产品定位

## 2.1 产品定位

一款通过虚拟角色养育和周期性任务，帮助用户持续存钱、建立储蓄习惯的轻量级养成类应用。

## 2.2 核心价值

产品主要解决以下问题：

1. 用户缺少明确的存钱理由；
2. 用户容易中断储蓄计划；
3. 普通记账应用缺乏情感连接和持续反馈；
4. 用户希望通过轻量游戏化方式获得存钱动力；
5. 用户需要一个简单的本地工具记录自己的储蓄过程。

## 2.3 核心使用场景

用户创建一只虚拟猫咪，并配置猫粮。

猫粮按照设定的每日消耗量逐渐减少。当库存即将耗尽或已经耗尽时，系统生成一条任务：

> “小猫的猫粮快吃完了，建议存入 ¥35，为小猫储备下一份猫粮。”

用户随后在应用外，将 ¥35 存入自己的储蓄账户，回到应用后点击：

> “我已存入”

应用记录本次存入金额，并增加猫粮库存，同时更新用户累计存入金额。

# 三、产品核心流程

## 3.1 首次使用流程

```text
打开应用
    ↓
查看产品说明
    ↓
了解资金不会被应用自动扣除
    ↓
创建养育对象
    ↓
选择类型：婴儿 / 猫 / 狗
    ↓
设置名称和头像
    ↓
选择或配置商品
    ↓
设置每日消耗量和参考价格
    ↓
设置初始库存
    ↓
进入养育主页
```

## 3.2 日常使用流程

```text
系统根据时间计算商品消耗
    ↓
商品库存逐渐减少
    ↓
库存即将耗尽
    ↓
生成储蓄任务
    ↓
用户在应用外主动存入资金
    ↓
回到应用点击“我已存入”
    ↓
填写实际存入金额
    ↓
任务完成
    ↓
商品库存增加
    ↓
累计存入金额更新
```

## 3.3 任务完成流程

用户点击任务后，进入任务详情页，页面展示：

- 养育对象名称；
- 商品名称；
- 当前库存；
- 建议存入金额；
- 参考价格区间；
- 任务产生时间；
- 当前任务状态；
- 备注信息。

用户在应用外完成存钱后，点击：

> 我已存入

然后填写：

- 实际存入金额；
- 存入时间；
- 备注；
- 是否使用自定义金额。

提交后：

1. 任务状态变更为“已完成”；
2. 保存一条存钱记录；
3. 增加对应商品库存；
4. 更新角色状态；
5. 更新累计存入金额；
6. 记录任务完成时间。

# 四、核心概念定义

## 4.1 累计存入

表示用户在应用中记录的所有储蓄金额总和。

不建议使用以下名称：

- 总消费；
- 已消费；
- 花费金额；
- 购买金额。

建议使用：

- 累计存入；
- 累计储备；
- 养育基金；
- 已完成金额；
- 储蓄总额。

首页可以显示：

```text
累计存入
¥1,280
```

同时显示：

```text
本月存入 ¥350
当前待完成 ¥68
```

## 4.2 建议存入金额

系统根据商品参考价格生成的建议金额。

例如：

```text
猫粮库存已不足
建议存入：¥35
参考范围：¥30～¥45
```

用户可以按照自己的实际情况修改存入金额。

## 4.3 商品库存

库存不是简单的“购买次数”，而是当前商品可以支持角色使用的剩余数量。

例如：

- 奶粉：剩余 350 克；
- 猫粮：剩余 420 克；
- 猫砂：剩余 2.5 千克；
- 纸尿裤：剩余 18 片。

初版也可以简化为整数包装数量，但建议底层数据支持小数和具体单位。

## 4.4 任务

任务表示系统建议用户完成的一次储蓄行为。

任务不等于真实消费，也不等于真实购买。

任务状态可以包括：

- 待完成；
- 已完成；
- 已跳过；
- 已延期；
- 已过期；
- 已撤销。

## 4.5 存钱记录

存钱记录表示用户实际在应用中记录的一笔储蓄。

一笔存钱记录可以对应一个任务，也可以是用户主动新增的储蓄记录。

## 5.4 消耗速度配置

商品消耗速度不应完全写死，需要允许用户调整。

例如奶粉消耗会受到以下因素影响：

- 婴儿年龄；
- 每日喂养次数；
- 每次用量；
- 奶粉规格；
- 喂养方式；
- 宠物体重；
- 宠物年龄；
- 饮食习惯。

用户可以配置：

- 每日消耗量；
- 商品包装规格；
- 初始库存；
- 是否启用自动消耗；
- 是否生成任务；
- 任务触发阈值。

### 示例

```text
商品：奶粉
包装规格：800 克
每日消耗：120 克
初始库存：800 克
预计使用时间：约 6.7 天
```

计算公式：

```text
预计使用天数 = 当前库存 ÷ 每日消耗量
```

## 5.5 库存消耗系统

商品库存按照用户设定的消耗速度自动减少。

应用不依赖后台持续运行的计时器，而是保存时间点，在用户打开应用时进行补算。

### 核心时间字段

- `lastConsumedAt`：上次计算库存的时间；
- `nextEventAt`：预计下一次事件时间；
- `currentStock`：当前库存；
- `dailyConsumption`：每日消耗量。

### 补算逻辑

```text
经过时间 = 当前时间 - 上次计算时间
消耗量 = 经过天数 × 每日消耗量
当前库存 = 当前库存 - 消耗量
```

当应用重新启动时：

1. 读取上次计算时间；
2. 计算经过的时间；
3. 补算商品消耗；
4. 更新当前库存；
5. 判断是否需要生成任务；
6. 保存新的计算时间。

### 时间异常处理

需要考虑：

- 用户长时间未打开应用；
- 手机重启；
- 应用被系统杀死；
- 用户修改系统时间；
- 时区发生变化；
- 角色被暂停；
- 商品配置发生修改。

初版可以采用以下规则：

- 只在打开应用时计算；
- 暂停角色时停止消耗；
- 修改每日消耗量后，从修改时间开始使用新规则；
- 如果检测到系统时间异常，提示用户确认；
- 库存最低不低于 0。

## 5.6 事件和任务系统

### 任务生成条件

当商品库存低于设定阈值时，生成储蓄任务。

例如：

```text
猫粮剩余不足 1 天
    ↓
生成“储备猫粮”任务
```

任务不一定要等到库存完全为零才生成，否则用户可能来不及完成储蓄。

### 任务内容

任务包含：

- 任务 ID；
- 角色 ID；
- 商品 ID；
- 任务类型；
- 建议存入金额；
- 参考价格；
- 创建时间；
- 截止时间；
- 当前状态；
- 实际存入金额；
- 完成时间；
- 用户备注。

### 任务示例

```text
任务名称：为小橘储备猫粮
商品：猫粮
建议存入：¥35
当前库存：剩余 0.8 天
状态：待完成
```

### 任务频率控制

为了避免用户产生压力，需要支持：

- 事件频率控制；
- 暂停角色；
- 暂停商品；
- 任务合并；
- 延期处理；
- 宽限期；
- 低频模式；
- 自定义难度。

可以提供三种模式：

#### 轻松模式

- 每月产生 1～2 次任务；
- 多个商品任务自动合并；
- 适合刚开始存钱的用户。

#### 标准模式

- 按照商品消耗速度生成任务；
- 适合正常使用。

#### 挑战模式

- 增加可选突发事件；
- 允许设置每月上限；
- 不建议默认开启。

# 六、数据和代码设计

## 6.1 配置数据和运行数据分离

商品默认参数属于配置数据，可以放在本地配置文件中。

例如：

```text
config/
  companion_templates.json
  product_configs.json
  event_configs.json
```

商品配置文件只保存固定模板，例如：

```json
{
  "id": "cat_food",
  "name": "猫粮",
  "category": "FOOD",
  "unitName": "克",
  "packageSize": 2000,
  "packageUnit": "克",
  "dailyConsumption": 80,
  "defaultPriceFen": 3500,
  "minPriceFen": 3000,
  "maxPriceFen": 4500
}
```

以下数据不应放在配置文件中：

- 当前库存；
- 用户实际存入金额；
- 任务完成状态；
- 用户自定义价格；
- 商品上次消耗时间；
- 存钱记录；
- 用户创建的角色。

这些数据属于运行时数据，应保存在本地数据库中。

## 6.2 数据模型示例

### 角色

```kotlin
data class Companion(
    val id: String,
    val type: CompanionType,
    val name: String,
    val avatar: String,
    val background: String,
    val createdAt: Long,
    val isPaused: Boolean
)
```

### 商品配置

```kotlin
data class ProductConfig(
    val id: String,
    val name: String,
    val category: ProductCategory,
    val unitName: String,
    val packageSize: Double,
    val packageUnit: String,
    val dailyConsumption: Double,
    val defaultPriceFen: Int,
```

金额统一使用整数分，避免使用 `Double` 处理金额：

```kotlin
val defaultPriceFen: Int
```

# 七、推荐技术架构

如果项目采用 Android Jetpack Compose，建议使用以下架构：

```text
Compose UI
    ↓
ViewModel
    ↓
UseCase
    ↓
Domain Engine
    ↓
Repository
    ↓
Room + DataStore
```

## 7.1 UI 层

负责：

- 展示页面；
- 接收用户操作；
- 显示加载状态；
- 显示错误信息；
- 展示任务和统计结果。

Compose 不负责：

- 商品消耗计算；
- 任务生成；
- 金额统计；
- 数据持久化；
- 时间补算。

## 7.2 ViewModel 层

负责：

- 管理页面状态；
- 调用 UseCase；
- 响应用户操作；
- 触发数据刷新；
- 向 UI 提供统一状态。

## 7.3 Domain 层

核心逻辑建议独立设计：

```text
ConsumptionEngine
TaskGenerator
SavingCalculator
InventoryCalculator
StatisticsCalculator
```

### ConsumptionEngine

负责：

- 根据时间计算商品消耗；
- 更新当前库存；
- 处理暂停和恢复；
- 处理时间异常。

### TaskGenerator

负责：

- 判断是否需要生成任务；
- 防止重复生成任务；
- 合并多个商品任务；
- 应用任务频率规则。

### SavingCalculator

负责：

- 计算累计存入；
- 计算本周、本月存入；
- 计算各角色和各商品金额。

## 7.4 Data 层

负责：

- Room 数据库；
- DataStore 设置；
- 本地配置读取；
- Repository 实现；
- 数据迁移；
- 数据备份和恢复。

```text

    ↓

    ↓

    ↓
```

# 十二、最终产品方向

本产品不应被定义为：

> 假装养孩子或宠物，并模拟真实消费。

更适合的产品定位是：

> 用虚拟角色和周期性任务，帮助用户建立持续储蓄习惯。

产品的核心不是复杂的养成画面，而是以下四个模块：

1. 商品配置；
2. 时间消耗引擎；
3. 任务生成器；
4. 存钱记录系统。

只要这四个模块设计稳定，后续就可以比较容易地增加：

- 新角色；
- 新商品；
- 突发事件；
- 统计图表；
- 成就系统；
- 旅行基金；
- 教育基金；
- 应急基金；
- 房屋装修目标。

因此，第一版应优先完成一个简单、清晰、可持续使用的闭环，而不是一开始实现大量角色、复杂动画和真实支付功能。
